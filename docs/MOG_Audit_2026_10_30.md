## 1. What this project is

MOG (Master Ordering Guide) is the ordering system for Happy Endings Hospitality's stores: ten live instances across four concepts (Roll Play, Teas'n You, Lei'd Poke, ĂN), plus a master template.

Each store has three pieces:

1. **A static PWA** at `https://sebheh.github.io/mog-mobile/<slug>/`, built by [build.py](../build.py) from [template/index.html](../template/index.html). It is one HTML file with no bundler and no framework, plus a service worker.
2. **A Google Sheet with a bound Apps Script project** (11 clasp targets, one per store plus `_template`). The script still owns the Sheet menus, the 3:30 AM cycle close, the recap email and the onboarding moves.
3. **A row in one shared Supabase project** (`mog` schema, functions-only access). Since October 2026 the phones read and write counts there directly, and the catalog is edited in the app.

**What a kitchen manager does with it:** signs in with a 4–8 digit store PIN, opens today's vendors, types on-hand counts (or steps them), sees a suggested order quantity computed from par, pack, on-hand, a per-vendor day-of-week multiplier and an optional emergency override, reviews the order, copies it as an email to the vendor, and marks it reviewed. At 3:30 AM the cycle closes: the order is logged, counts are cleared, and a recap email goes to the store's recipients.

**What it is trying to become** (from [MOG_OneApp_Spec.md](MOG_OneApp_Spec.md) and [MOG_ProjectNotes.md](MOG_ProjectNotes.md)):

- **The Sheet is out of the hot path.** Supabase is the operational store; the Sheet keeps the Apps Script and receives a nightly `LOG_ORDERS` backup.
- **One app per store.** Phones count and order; computers do the same plus an Editor (Items, Vendors, Storage areas, Shelf to Sheet, Order history, Health check, Changes, Overview).
- **One copy of the order math.** `apps-script/OrderMath.gs` runs on the server and is copied verbatim into the phone by `build.py`; the gates compare the two and compare both against an older revision.
- **One writer per kind of data.** No bidirectional sync between Sheet and Supabase.
- **Permanent URLs.** A store's `/<slug>/` is never renamed.

**Constraints that shape the code:** no bundler, one page per store, 11 identical Apps Script projects, a shared PIN (no per-user accounts), and deploys that fan out to 11 targets.

### What is in good shape

Worth saying plainly, because it changes what a fix should look like:

- **The gate suite is unusually strong for a repo of this type.** 24 gates, real `.gs` code under Node, planted-defect controls that must bite, randomized stores, and a public-surface gate ([tests/public_surface.test.js](../tests/public_surface.test.js)) that enforces the "every server function is private unless reviewed" rule.
- **The migration design is documented and followed.** Schema versions are re-runnable, grants are closed then opened explicitly, PINs are bcrypt-hashed, session tokens are stored hashed, and every `security definer` function I read sets `search_path = ''`.
- **`build.py` is idempotent and fails loud** on a missing or duplicated placeholder. I re-rendered all ten stores and both editors in memory: the committed output is byte-identical to a fresh build, modulo CRLF. Nothing is stale.
- **`.clasp-targets.json` and `stores.json` agree** on all ten `/exec` URLs, and the template target is present.
- **No shared-constant drift** across `.gs` files (the scanner's lens 3 is clean), and no store-specific data hardcoded in `.gs`.

### Do first (they change what ships, or they cost nothing)

**#20 [MED value, LOW effort] The deploy router cannot say "build AND redeploy", and it misroutes the order math.**
[.claude/skills/mog-deploy-workflow/scripts/route.py](../.claude/skills/mog-deploy-workflow/scripts/route.py) classifies each file to one action (lines 43–83) and takes the maximum across files (line 123). CONFIRMED by running it:

- `route.py apps-script/OrderMath.gs` prints **`python deploy.py`** with "bound-sidebar .gs logic reads HEAD". Wrong twice: `OrderMath.gs` is copied into every store page by `build.py`, so a change needs `python build.py` too, and it is loaded by `/exec` through `MOGApi.gs`'s builders, so it needs `--redeploy`.
- `route.py template/index.html apps-script/MOGApi.gs` prints only `--redeploy`, silently dropping the `build.py` step for the template change.

A single-valued action cannot express the repo's most common real change. → Make the router return a **set** of required actions and print every one, add a `BUILD + REDEPLOY` case for `OrderMath.gs`, make `appsscript.json` route to `--redeploy` when its `webapp` block changes, and add a gate that pins these cases.
*Verification:* `python .claude/skills/mog-deploy-workflow/scripts/route.py apps-script/OrderMath.gs` prints both commands.

**#21 [MED value, LOW effort] CI never checks that the generated store folders match the template.**
[.github/workflows/gates.yml](../.github/workflows/gates.yml) runs only `node tests/run_all.js`. No gate reads `<slug>/index.html`, and no step runs `build.py`. So a pull request that edits `template/index.html` or `stores.json` and forgets `python build.py` passes CI and deploys ten stale store pages. The inverse also passes: a hand-edited `rpr/index.html` would not be caught. This is the repo's own pitfall #3 and invariant #1, and it is the one thing CI does not cover.

→ Add a `tests/build_output.test.js` (or a CI step) that renders the expected output the way `build.py` does and compares it to the committed dirs with line endings normalised, and that runs `python build.py --dry-run` to validate `stores.json`. The script used for this audit is a starting point (render `template/index.html` with the six substitutions, compare, then compare `editor/`).

**#22 [MED value, LOW effort] The gate suite is red on a Windows checkout, and the docs tell people to run it.**
[tests/slice_js_selftest.js](../tests/slice_js_selftest.js) reads `slice_js.js` from disk (line 13) and its control anchors contain `\n` (lines 125–135). With `core.autocrlf=true` the file is CRLF, so three anchors match zero times and the run fails. `plant()` in [tests/fake_apps_script.js](../tests/fake_apps_script.js) was fixed for exactly this class on 2026-10-29, but the selftest does not use it. CONFIRMED: the LF copies pass. [MOG_CurrentState.md](MOG_CurrentState.md) and the 10-29 handoff both claim it passes on the Windows checkout, and [tests/README.md](../tests/README.md) says to run it before every deploy. Both maintainers are on Windows, so the instruction is currently unfollowable and trains people to ignore a red gate.

→ Normalise newlines once (`const SRC = raw.replace(/\r\n/g, '\n')`) or make the control find/replace EOL-agnostic, and add a control that proves it (run the whole selftest on both EOLs).

### Security and data integrity

**#24 [MED value, MED effort, DECISION] The PIN policy makes a store lockable by a stranger and enumerable over time.**
PINs may be 4 digits ([Editor.gs:312](../apps-script/Editor.gs), [Admin.gs:24](../apps-script/Admin.gs)), the only rate limit is 5 failures then 5 minutes ([MOGApi.gs:163](../apps-script/MOGApi.gs), [schema.sql:292](../supabase/schema.sql)), and the lockout is checked **before** the PIN, so the master PIN is blocked too. The store slug is public in every app URL. So five bad requests every five minutes keeps every KM at that store on the PIN screen, indefinitely, on both `/exec` and Supabase. In the other direction, 5 tries per 5 minutes is 1,440 a day, which walks a 4-digit space in about a week. Clearing it needs the Sheet menu (`clearPinLockout_`) or a session, and a locked store cannot get a session ([schema_v9.sql:751](../supabase/schema_v9.sql)).

This is a design decision, not a bug. Options: raise the minimum to 6 digits on new or changed PINs; exponential backoff (5 min, 15 min, 1 h); a separate counter so the master PIN still works during a store lockout; or a lockout clear that the app can perform from a signed-in device on the same network. Ask before changing.

**#25 [LOW value, LOW effort] `mog_sync_set_state` accepts any cycle date.**
[supabase/schema.sql:599](../supabase/schema.sql) takes `p_cycle_date` from the caller with only a day-of-week check. The cycle date decides which counts are current, and `snapshot_json` compares it to the store's local today for "stale". A Sheet with a wrong AE9/AE2, or a bad call, moves the store's cycle arbitrarily. CONFIRMED no bound; PLAUSIBLE impact (needs a Sheet misconfiguration to trigger). → Reject a date more than ~7 days from the store's local today, and log the refusal.

**#26 [LOW value, LOW effort] The count path accepts an unbounded rows array.**
[supabase/schema.sql:157](../supabase/schema.sql) (`mog.upsert_counts`) caps the length of a vendor and item name but not the number of rows; `mog_sync_put_counts` and `mog_save_counts` pass arrays straight through. The editor caps ops at 5,000 ([schema_v6.sql:481](../supabase/schema_v6.sql)); the count path has no equivalent. → Cap at ~2,000 rows and return a normal envelope error. A real save is in the hundreds.

**#27 [LOW value, LOW effort] `/exec` and Supabase disagree on a junk `onHand`.**
[MOGApi.gs:789](../apps-script/MOGApi.gs) does `Number(it.onHand)` and can write `NaN`; `mog.to_onhand` ([schema.sql:127](../supabase/schema.sql)) maps junk to `null`, which is a cleared count. The current PWA sends `null` or a number, so this is latent (PLAUSIBLE; the cell effect of `NaN` was not measured). → Mirror `to_onhand`: blank or non-finite becomes `''`.

### Correctness, now diagnosed (these were already on the held-back list; do not renumber)

**H1. A same-day manual close destroys that day's order log at the next 3:30 AM close.**
Confirmed by tracing the code. Day N at 17:00, the Sheet menu calls `closeCycleInDb_({sameDay:true})` ([ResetLog.gs:333](../apps-script/ResetLog.gs)). It logs N's rows and sets `cycle_date = N` again ([schema_v2.sql:295](../supabase/schema_v2.sql)), so the state cannot tell "already closed and restarted" from "still open". At 03:30 on N+1, `nightlyMaintenance_` closes `closing = N` with no `sameDay`, which passes the `closing < today` guard. `mog_sync_close_cycle` **deletes** N's `order_log` rows (line 282) and inserts none, because the counts are now empty; `appendLogBackup_(N, [])` does the same to `LOG_ORDERS`, and the recap is rebuilt from an empty log, so no email goes out. The day's order history is gone from both stores.

→ Add `last_closed_date` to `mog.store_state` and set it on every close. When a close's `p_closing <= last_closed_date` and it is not an explicit `sameDay` re-close, still advance the cycle but **skip the log replacement**: no delete and no insert in `mog.order_log`, and no `deleteLogEntriesForDate_` in the Sheet backup. That keeps the day's log and still starts the new day. A `sameDay` close keeps its replace semantics. One column and two guards; it also stops a manual `resetOnHandAllVendors_` from double-logging. Needs a schema version and smoke rows.

**H2. Turning the Emergency Override off before 3:30 changes what gets logged and emailed.**
The order log is computed at **close** time from live state (`orderLogRowsFromInputs_` over `supabaseSnapshot_`, [Sync.gs:447](../apps-script/Sync.gs)), not accumulated as people count. So the override flag and the per-vendor picks at 03:30 decide the quantities and which vendors appear. Turning the override off in the evening drops every vendor whose base multiplier is 0 for that day, and rescales the rest. Same for the recap, which rebuilds from the log. This is the second held-back item and the mechanism is the same: the log is a snapshot of state at close, not of decisions made during the day.

→ Three shapes, pick one with Sebastian: (a) persist the override context on each count row and build the log from those rows; (b) snapshot the override state when the first vendor is marked reviewed, and use that snapshot at close; (c) refuse to turn the store-wide override off, or clear a vendor pick, while the current cycle has any counts, unless the KM confirms that the day's log will change. (c) is a guard rather than a fix, and it is the smallest.

### Tooling and docs

**#28 [LOW value, LOW effort] The app's EN/ES switch leaves an open Manage page in the old language.**

PLAUSIBLE (not reproduced in a browser). → In `setLang`, when `state.currentView === 'manage'` and the frame is loaded, update `mog_edit_lang` and reload the frame (or `postMessage` and re-render in `host.js`).

**#34 [LOW value, LOW effort] `build.py`'s reserved slugs miss real top-level folders.**
[build.py:77](../build.py) reserves `template`, `sw.js`, `manifest.webmanifest`, `stores.json`, `build.py`, `readme`, `readme.md`, but not `docs`, `tests`, `icons`, `supabase` or `editor`. `SLUG_RE` accepts all of those. **#35 [LOW value, LOW effort] `deploy.py` says `--redeploy` skips the template, but it redeploys it.**
[deploy.py:349](../deploy.py) help text says "skipped for template"; `redeploy_target` runs for any target with a `deploymentId`, and `_template` has one. → Either skip `isTemplate` in `cmd_deploy` or fix the text. (The template has no `/exec`, so skipping is the cheaper answer.)

**#36 [LOW value, MED effort, DECISION] A partial recap send is recorded as sent.**
[Recap.gs:372](../apps-script/Recap.gs) sets `MOG_LAST_RECAP_SENT_DATE` and stops when `sent > 0`, even if some recipients failed; failures are only logged. For a GM whose address bounced, the recap is silently missing and no path retries it. The comment says "at most one DELIVERED email per cycle", so this may be deliberate. → Keep the failed addresses in the pending record and re-arm for just those, or document the trade-off in the runbook.

**#37 [LOW value, LOW effort] A failed order-log backup silently suppresses the recap.**
[Sync.gs:460](../apps-script/Sync.gs) logs and ignores an `appendLogBackup_` failure, then schedules the recap, which rebuilds from `LOG_ORDERS` ([Recap.gs:352](../apps-script/Recap.gs)). If the Sheet write failed, the recap finds nothing and sends nothing, while the log line says only that the backup failed. → On a backup failure, use `sendRecapRowsNow_(closing, rows)` (the rows are already in hand) instead of the async path.
